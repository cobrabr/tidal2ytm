# AGENTS.md

Python CLI (`tidal2ytm`) that transfers Tidal liked tracks to YouTube Music — album-anchored matching with duration and fuzzy fallbacks, managed with `uv` from the repo root.

## Workflow

0. `tidal2ytm auth [--ytm-only|--tidal-only] [--re-auth] [--client-id X --client-secret Y]` — create or refresh OAuth tokens. Default authenticates both YTM and Tidal; a provider whose cached token still validates is skipped. YTM flow wraps `ytmusicapi.setup.setup_oauth`; Tidal flow wraps `tidalapi.Session.login_oauth`.
1. `tidal2ytm` (no args) — main-menu gateway (`planning.py`): fetch `tidal_source.py:get_favorite_tracks` once → search/filter locally → accumulate a selection → explicit match via `matcher.py:match_track` → merge into `data/transfer_plan.toml`, with review (`r`), transfer pending (`t`), dry-run (`d`), and auth (`a`) from the main menu; the `review`/`transfer`/`auth` subcommands remain as scriptable equivalents. Done when the selection is matched, `transferred` tracks are skipped, and `[meta]` is recomputed via `plan_io.py:update_plan_meta`. Improved matches prompt `[y/N]` per track unless the `ctrl+o` override banner is on.
2. `tidal2ytm review` — rich TUI for low-confidence matches. Done when the first write triggers `backup_plan()` to `transfer_plan.YYYYMMDD_HHMMSS.toml` and decisions persist immediately.
3. `tidal2ytm transfer --track <11-char-id> | --album <match_id> | --artist <match_id> | --all [--dry-run]` — exactly one scope required. Done when `transfer.py` batches in-memory updates, backs up once, and writes atomically at end (plus once on first failure); `pending` → `transferred`/`failed` reflected in `[meta]`.
4. `tidal2ytm status [--artist <match_id>] [--album <match_id>]` — offline-safe. Smoke test: `tidal2ytm --help` succeeds.

`uv run tidal2ytm <subcmd> ...` works equivalently from the repo root and is preferred when iterating on the source.

`sidecar/` is a second uv workspace member (`tidal2ytm_sidecar`) holding the NDJSON sidecar: `protocol.py` owns the wire envelopes, `ops.py` answers questions about the outside world, `runner.py` is the read/answer loop, and `sidecar_logging.py` reads the host-supplied level. Three more files are the packaging layer, and all three exist because Tauri stages a single frozen executable: `build_sidecar.ps1` drives PyInstaller and copies the result into `src-tauri/binaries/` under the host triple, `tidal2ytm-sidecar.spec` is the onefile build recipe, and `tidal2ytm_sidecar_entry.py` is the entry script. That entry script is load-bearing and deliberately *not* `__main__.py`: PyInstaller freezes the entry script as a bare `__main__` with no `__package__`, so the package's relative `from .runner import main` fails inside the built artefact and only once it runs. `contracts/*.json` is the cross-language wire contract, asserted by both the Python and the Rust suites.

`crates/`, `src-tauri/`, and `src/` are the desktop GUI's three roots. `crates/tidal2ytm-core`, `crates/tidal2ytm-ipc`, and `crates/tidal2ytm-store` are Tauri-free libraries — `Cargo.toml`'s `default-members` is what keeps a bare `cargo test` off the host on a Linux runner with no webkit — and `Cargo.lock` plus `pnpm-lock.yaml` are committed, so CI's frozen installs match. `crates/tidal2ytm-store` owns the SQLite schema, the migration runner and every SQL statement in the project, over `rusqlite` bound to bundled stock SQLite — `libsql` was replaced after its bundled build corrupted its heap inside `sqlite3ExprCodeTarget` under concurrent use, at the cost of Turso's unused remote sync protocol: `schema.rs` is the program design's DDL with no local edits, `migrate.rs` applies it against `PRAGMA user_version`, and `store.rs` holds `Store` and its operations, including `write_status`, the only function that assigns the status of a row that already exists (`upsert_track` inserts new rows as `'pending'` and skips the update entirely over a transferred one). `src-tauri/` is the host package (`tidal2ytm`, library target `tidal2ytm_host`): `sidecar_path.rs` works out how to start the sidecar, `state.rs` owns the client and the wire-shaped `AuthStatus`, `commands.rs` is the command surface, `jobs.rs` is the job manager and per-job state, `sync.rs` is the sync job loop, `logging.rs` is the per-run log file sink with rotation, and `main.rs` is the entry point. `capabilities/default.json` grants `core:default` plus dialog, app-data read/write, and opener scoped to `$APPDATA/**`. `src/` is the Svelte 5 frontend, and `src/lib/ipc.ts` is the only place `invoke` is called.

## Quality gates

`pyproject.toml` defines `tool.ruff`, `tool.pyright` (`typeCheckingMode = "strict"`, `reportMissingImports = false`), `tool.pytest`, and `tool.coverage` with an enforced `fail_under = 80` gate over both workspace members. The pre-commit, pre-push, and GitHub Actions workflows exercise these tools. Reproduce them locally with:

- `uv run ruff check .`
- `uv run ruff format --check .`
- `uv run pyright`
- `uv run pytest -q`
- `uv run pytest --cov --cov-report=term-missing -q`
- `pnpm format` → `pnpm lint:fix` → `pnpm lint` → `pnpm format:check` → `pnpm check` → `pnpm test` → `pnpm build`
- `cargo fmt --all --check` · `cargo clippy -p tidal2ytm-core -p tidal2ytm-ipc -p tidal2ytm-store --all-targets -- -D warnings` · `cargo test -p tidal2ytm-core -p tidal2ytm-ipc -p tidal2ytm-store`
- `cargo clippy -p tidal2ytm --all-targets -- -D warnings` · `cargo test -p tidal2ytm` — the host's own pair, and **not** runnable until `src-tauri/binaries/tidal2ytm-sidecar-<triple><.exe>` and `dist/` exist (see the build invariant below). `cargo fmt --all --check` is workspace-wide, so it gates `src-tauri/` from either job.
- The golden corpus the `crates/tidal2ytm-core` parity tests replay is regenerated with `uv run python crates/tidal2ytm-core/tools/generate_fixtures.py`, never by CI, so the fixture diff is the review artifact for an intentional rule change.

Tests use fictional artist/track names and synthetic IDs only, never real catalogue data.

## Dependency updates

Three ecosystems, three lockfiles, three commands. Dependabot opens security pull requests and nothing else — see `.github/dependabot.yml`. Everything else is deliberate, one ecosystem at a time, because a bulk upgrade that breaks CI is indistinguishable from a bulk upgrade that found a real incompatibility.

| Ecosystem | Command | Updates |
| --- | --- | --- |
| Python | `uv lock --upgrade` | `uv.lock`, within the ranges `pyproject.toml` declares |
| Frontend | `pnpm update --latest` | `pnpm-lock.yaml` and the exact pins in `package.json` |
| Rust | `cargo update` | `Cargo.lock` only — a version in `Cargo.toml` is a hand edit |

Every one of these is followed by the full gate set and a single-purpose commit. Bump one ecosystem per commit; a three-ecosystem diff is unreviewable. Check the resulting diff for a `^` or `~` appearing in `package.json`: every pin here is exact, and a range is how a release someone else published becomes this project's outage.

`ruff` has no version of its own to move. It is an ordinary dependency: the pre-commit hook runs `uv run ruff` and the `check` job runs `uv run ruff check .`, so both read `uv.lock` and there is no second pin to keep in step. The cost of that is real, so it is stated here: a ruff release can add a rule inside the families this project selects (`E`, `F`, `W`, `C90`, `I`, `N`, `UP`, `S`, `B`, `SIM`, `RUF`) and turn the gate red with no edit to any code, so run `uv run ruff check .` and `uv run ruff format --check .` **after** `uv lock --upgrade` and not only after a change to a `.py` file. Ruff has formatted the Python code blocks inside Markdown since 0.16.0, so `ruff format --check .` covers this file and `README.md`, and the `ruff-format` hook rewrites those blocks instead of skipping them: the code blocks in both files are formatted, not excluded, and `docs/superpowers/**` is the only thing `[tool.ruff.format]` excludes. The workflow's `paths-ignore: ['**.md']` sits at workflow level, so a Markdown-only push still queues no run at all and CI cannot reach either file by itself — that is the remaining gap, and it is why a malformed code block here is caught by whichever commit happened to touch something else.

`uv lock --check` is the local form of what CI's `uv sync --locked` asserts. Use `--locked`, never `--frozen`, in CI: `--frozen` installs whatever `uv.lock` says and never compares it to `pyproject.toml`, so a manifest edit that was never re-locked goes green and every Python gate then runs against a dependency set the manifest does not describe.

Three pins are not "latest wins". The `tauri` crate and `@tauri-apps/cli` are released in lockstep and must always match, so they move together. `typescript` is pinned to `6.0.3` because that is the ceiling, not the floor: it is the last pure-JS TypeScript, and both `svelte-check` and `typescript-eslint` drive TypeScript through the JS compiler API that the native TypeScript 7 does not ship. When a release lifts those peer ranges to include 7, take it deliberately, with `svelte-check` and `typescript-eslint` in the same commit — never as a side effect of `pnpm update --latest`. `pyinstaller` is the same kind of pin and for a sharper reason: it is exact in the `build` dependency group because `sidecar/tidal2ytm-sidecar.spec` documents `disable_windowed_traceback`'s default against the version that builds it, and an `==` pin is the only thing that makes the documentation true. `uv lock --upgrade` will not move it, so bumping it is a hand edit to `pyproject.toml` plus `uv lock`, and the cost is paid on every Linux runner because `check` syncs `--all-groups` for a tool nothing there runs.

After any bump, re-read the peer constraints rather than trusting the resolver: `pnpm install` failing on a peer conflict means the answer is a different version, not `--force`.

## CI parity (CI is Linux-only; dev is usually Windows)

- CI (`.github/workflows/ci.yml`, ubuntu-latest) has a `changes` job plus four gate jobs, and `check` is the only gate with no filter so it runs for every non-markdown change. `check` runs `check-toml`, `ruff check`, `ruff format --check`, `pyright`, then the full suite as `uv run pytest --cov --cov-fail-under=80 --cov-report=xml --cov-report=term-missing` (no `-x`, no `-q`) — `uv sync --all-groups` already installs the `sidecar` workspace member through the `dev` group, so the sidecar's 34 tests are in that suite. `rust` runs `cargo fmt --all --check`, clippy, and `cargo test` for `crates/tidal2ytm-core` + `crates/tidal2ytm-ipc` + `crates/tidal2ytm-store`, and does `uv sync --all-packages` **before** `cargo test` because `crates/tidal2ytm-ipc/tests/round_trip.rs` spawns the real Python sidecar and would otherwise degrade to a bare `python3`. `host` builds the frontend, then runs clippy and `cargo test -p tidal2ytm`. `frontend` runs five of the seven `pnpm` gates — `format:check`, `lint`, `check`, `test`, `build` — and the other two, `format` and `lint:fix`, are the pre-commit hook's rewriting pair rather than gates: CI must check and never rewrite. Run the exact sequence before pushing — the pre-push hook's `pytest -q -x` can hide order-dependent and coverage-path failures.
- **Job selection is a `changes` job, not a job-level `paths:` key.** `paths` and `paths-ignore` exist only on triggers (`on.push` / `on.pull_request`); a job-level one is rejected by GitHub's workflow schema and makes the whole file invalid, so GitHub creates no job at all and the run fails in 0 seconds with the workflow file path as its name. `rust`, `host` and `frontend` therefore carry `needs: changes` plus an `if:` that reads a boolean from a single `dorny/paths-filter` step in `changes`, which lists the same paths once; `check` stays unfiltered. A filter must list every path that can make its job fail, and a job cannot be dropped from a list to save a runner: `crates/**` was missing from `rust`, `crates/**` and `sidecar/**` were missing from `host`, and `src-tauri/` is outside `Cargo.toml`'s `default-members`, so nothing else compiled or tested the host's crates at all. `host` needs `crates/**` because it is the only job that compiles `tidal2ytm-ipc`'s consumer or runs the host's tests — `rust`'s share of a crate change is clippy, that crate's own tests, and a workspace-wide `cargo fmt --all --check`, and none of the three compiles `src-tauri`. A rename the round-trip suite also imports turns `rust` red as well, so that entry is not the only thing between a crate change and a red run; it is the only thing between a crate change and a host that was built at all. The `host` job also runs `cargo fmt --all --check` because `rust` is filtered out of `src-tauri/**` and `cargo fmt` is workspace-wide. Overlapping patterns are expected: a path in two filters runs both jobs, and that is the intended cost, not a bug to optimise away. Because an invalid workflow file means CI never starts, no CI job can be the backstop for this one — the only gate over `.github/workflows/` is the `check-github-workflows` pre-commit hook, and `actionlint` is not used because its hooks need Go or Docker.
- **The hooks are a subset of CI, not a reproduction of it, and each hook names the files its tool owns rather than the files it runs on.** pre-commit ANDs `types` with `files`, and pre-commit-identify tags `Cargo.toml` as `cargo`, `Cargo.lock` as `cargo-lock`, `pyproject.toml` as `pyproject` and `contracts/auth_status.json` as `json` — none of them `rust` or `python` — so no hook in `.pre-commit-config.yaml` uses `types:` at all; `pyproject.toml` is where `[tool.ruff]`, `[tool.ruff.lint]`, `[tool.ruff.format]`, `[tool.pyright]`, `[tool.pytest.ini_options]` and `[tool.coverage.run]` all live, so a manifest-only commit has to run the gates that read it. A hook whose entry takes no path argument also needs `pass_filenames: false`: without it the `files` trigger hands the tool a manifest, `ruff check pyproject.toml` exits 0 without evaluating any config against any code, and the gate fires on exactly the commits that can break it while checking nothing. No hook sets `require_serial`, because pre-commit runs distinct hooks sequentially and `require_serial` only throttles parallelism inside one hook's file batches, which `pass_filenames: false` leaves empty. What still has no local hook at all is the frontend's `pnpm check`/`pnpm test`: a contract-only rename that breaks `src/lib/types.ts` is caught by the `frontend` job and by nothing before the push.
- Platform-branched code (`os.name`, `termios`/`msvcrt` guards) has a path CI exercises that Windows never does: force both branches in tests (monkeypatch `os.name`, stub the guarded import), because a green local run proves nothing about the Linux path. `sidecar/tidal2ytm_sidecar/runner.py:47`'s `for line in stdin` over a real pipe has never run on Linux — pytest feeds it a `StringIO` — and it is the most likely place a Windows-green test goes red on ubuntu-latest.
- Test doubles must implement the full interface production code touches (a stdin stand-in needs `fileno()` when the reader calls it); never stub narrower than the real collaborator. When production branches on a capability (`termios` import, `isatty`), the double must drive the same branch CI will take.
- **ALWAYS watch the CI run after a `git push`**: `gh run list` to find it, `gh run watch <run-id> --exit-status` to block on it. The pre-push hook runs on the dev platform, so local green proves nothing. Markdown-only pushes queue no run (`paths-ignore: ['**.md']`), so there's nothing to watch.

## Versioning

- `pyproject.toml:version` is the release number (bare `X.Y.Z`, no prefix). The feature branch sets the upcoming version once its scope is known (patch for bug fixes with no behaviour change, minor for new features and CLI surface changes, major for breaking `transfer_plan.toml` format or token/auth changes); no repeated bumps per change on the branch. Tags are created on `main` only, at release time.
- Keep `uv.lock` consistent: after bumping, run the gates once so the build rewrites the root-package version line, and stage `uv.lock` in the same commit. If the pre-commit pytest hook aborts with "files were modified", that rewrite is the cause — stage the lockfile and recommit.
- Tag the release commit with `git tag vX.Y.Z` (`v` prefix, matching `version`). Tags stay local unless the release is pushed.

## Invariants

- `tidal_id` is track identity; tracks have no `match_id`. Tracks are addressed by a bare 11-char `yt_video_id` — never a URL. `plan_io.py:extract_video_id` normalizes every accepted URL form. Video-id parsing is public `plan_io.extract_video_id`; first-party cross-module private imports in `tidal2ytm/` prod code are banned (pyright `reportPrivateUsage` must stay clean there; known exceptions are the test-file convention and justified third-party private access).
- `match_id` is `artist_slug`/`album_slug` with album slugs capped at 15 chars and `-2`/`-3` dedup. All slug logic lives in `slugs.py`.
- `TrackStatus` and `MatchMethod` are string enums whose `.value` matches the TOML representation; the persisted plan file is the source of truth for `pending | transferred | skip | failed | needs_review`.
- `[meta]` is recomputed via `plan_io.py:update_plan_meta()` after any status change. `transfer.py` calls it through `plan_io.save_with_meta` while `review.py` and `planning.py` use the `update_plan_meta` + `save_plan` equivalent (meta + atomic write); never call `save_plan` in a loop.
- Auth status has three states: `valid`, `refreshable`, `signed_out`. A refreshable session is signed in and will refresh itself; reporting it as signed out sends a working user to re-authenticate.
- The GUI mirror is grow-only: sync upserts and never deletes. A track's absence from one paginated fetch is not proof of absence from Tidal, and a delete would erase match state. A delete may only run against a fetch that completed every page, in one transaction, and never over a `transferred` or `skip` row.
- `upsert_track_source` never overwrites a `transferred` row: its `WHERE track.status <> 'transferred'` guard is byte-identical to `upsert_track`'s, and a sync write must not blank a match.
- `auth.py` owns token validity, client-secret reading, the tidal token schema, and the two token files' expiry formats — `ytm_expiry_iso` is why a `ytmusicapi` epoch integer never reaches the wire; `ytm_client.YTMClient` owns the session/header logic (WEB_REMIX swap for `/search?` and `/player?`) transplanted from `cli._ytm_login`. `cli.py` only wires argparse → runners.
- `paths.py` never touches disk on import. `ensure_logs_dir()` is called by `logging_setup.setup_logging`; `ensure_data_dir()` currently has **no production caller** — the CLI entry points stopped calling it and the sidecar only reads the token caches — so treat it as dead until something needs it rather than as a rule to follow. `STATE_FILE`/`REVIEW_FILE` were deleted; do not reintroduce stale path constants.
- `ytm_sink.add_track_to_library` uses `get_watch_playlist` + `edit_song_library_status` with `feedbackTokens.add`. `rate_song` / `LikeStatus.LIKE` only thumb-up a track and are wrong here.
- Logging is file-only: records go to the per-run `logs/` file, never to the console, and console behaviour never changes for the sake of logging. `logging_setup.py` owns levels, precedence, formatter, handler, and the per-run file; other modules only `logging.getLogger(__name__)` and emit — never reconfigure handlers or the root logger.
- `--log-level` flag beats `TIDAL2YTM_LOG_LEVEL` env beats default `INFO`; the accepted set is owned by `logging_setup.LOG_LEVELS`. An invalid env value is a hard CLI error, never a silent fallback. The GUI host passes the same env var to the sidecar at spawn, so the level applies even if the sidecar dies before its handshake.
- Log records never contain tokens, client secrets, or authorization headers; DEBUG payload logging uses `logging_setup.redact_payload` and logs payload shape (key names), never token values.
- `log_call`'s `except Exception` arm logs and always re-raises — a documented observer, not a suppressor; do not reuse the pattern to swallow errors elsewhere.
- Every module begins with `from __future__ import annotations`; data containers are dataclasses; public functions are type-annotated.
- `sys.exit` lives in `cli.main()` (and `--help` via argparse) plus the interactive error paths of `auth.run_ytm_auth` (missing/unparseable secrets, expired token). Library runners (`run_transfer`, `run_review`, logins, `YTMClient.login`) raise `errors.Tidal2YtmError` subclasses; tests assert raises, never `SystemExit` except at `main()`/auth-entry level.
- No `except Exception` / `suppress(Exception)` around auth probes: those catch the narrow `_AUTH_ERRORS` tuple only, so transport/auth bugs propagate instead of degrading into "re-authenticate" or "no match". Broad `except Exception` survives only at planning TUI crash barriers and in `ytm_sink`'s documented bool contract (returns `False` on failure).
- No `assert` for user-input validation; raise `ValueError`/`RuntimeError`. Narrow post-condition asserts remain in `planning.py`/`picker_rows.py`/`keys.py`. No `except SystemExit` except at planning TUI boundaries (absorb auth exits, keep the menu alive); no `except (X, Exception)` — the second arm subsumes the first.
- No `MagicMock`-tolerant production code (`hasattr` guards, try/except around attribute access). Boundaries validate (`SourceTrack.from_dict` raises `ValueError` on bad identity); tests still use `MagicMock` for YTM doubles (typed-fakes migration deferred).
- No nondeterminism in persisted ids: slug fallbacks hash (`sha1`), secret-file choice is `sorted()` + strict (0 → `FileNotFoundError`, >1 → `RuntimeError`), backup stamps include microseconds. `secrets`/random never feed plan content.
- One owner per constant: `DURATION_TOLERANCE_SEC`/`CONFIDENCE_THRESHOLD` live in `matcher.py`; `STATUS_STYLE` in `style.py`; confidence bands in `confidence.py`; text normalization in `text.py`. Duplicating a literal instead of importing is a review-blocking defect.
- Plan writes are atomic (temp + `os.replace`) with meta recomputed in the same call (`save_with_meta` in `transfer.py`; `update_plan_meta` + `save_plan` pair in `review.py`/`planning.py`); `update_track_in_plan` returns `bool` but current callers ignore it — check the return before relying on a `False` path. No per-track rewrite loops.
- Tidal token schema is `{token_type, access_token, refresh_token, expiry_time, user_id: int, country_code: str}`; both writers emit all six. Old files missing keys take the full-login path, never `KeyError`. Datetimes stay timezone-aware end to end.
- `transfer_plan.toml` accepts only `pending | transferred | skip | failed | needs_review`; unknown strings raise from `update_plan_meta`. Invalid video ids load as `""` + `needs_review` with a warning; corrupt TOML itself is fatal.
- TUI changes keep the readchar + fallback contract via `keys.read_key()` and one dispatch table per loop — never duplicate a keymap across `if use_readchar/else` branches. No new `C901 noqa` (`matcher.match_track` retains the one pre-existing noqa); split the function instead.
- Tests assert behaviour through public APIs with structural checks (membership, counts, outcomes), never exact colours/glyphs/whitespace/copy, never stdlib internals (`getsource`), never duplicated threshold suites. New constants need threshold-edge tests, not value locks.
- `contracts/auth_status.json` records the **signed-out** sample on purpose. `src/lib/types.ts` derives its payload types from that file and `Widen` turns the `null` literal into `string | null`, so replacing the sample with a signed-in payload silently narrows the frontend field to `string` and the nullable case stops compiling — the contract's key set is authoritative, its *values* are not.
- The sidecar's `expires_at` is an ISO-8601 UTC string or `None` and nothing else, and both providers go through `auth.py` (`tidal_expiry_iso` for the string `auth.py` itself writes, `ytm_expiry_iso` for the epoch integer `ytmusicapi` writes). `ops._cached` returns `dict[str, object]`, never `dict[str, Any]`: `json.loads` hands back `Any`, and `Any` launders through pyright in strict mode without a complaint, which is exactly how a raw epoch integer reached the wire while every gate stayed green. `dict[str, object]` plus the `_ProviderState` return types make removing either normalisation a `reportReturnType` compile error.
- The host's DEBUG log sink is installed by `run()`, never by `main()` alone, because `state::spawn` drains the sidecar's stderr into the `log` facade `run()` installed, and a facade with no sink is a no-op — so any entry point other than `run()` loses every record the process most likely to be complaining about arrives on. Level and logger are set as separate statements: `set_logger` failing skips `set_max_level`, and `MAX_LOG_LEVEL_FILTER` defaults to `Off`, so the skipped level is a silent loss of every forwarded diagnostic.
- `invoke` rejects with whatever a Rust command returned, and a command declared `Result<T, String>` therefore rejects with a **bare string**. `src/lib/ipc.ts` normalises every rejection into an `Error` so a screen can rely on `instanceof`; without that, a screen that checks `instanceof Error` shows a generic line and discards the only text that says what went wrong.
- The ruff gate is one binary: the project's own `ruff`, resolved by `uv.lock`, run by both the pre-commit hook and the `check` job. Never reintroduce a separately pinned ruff in the hook manifest. A hook with its own `rev` is a second owner for one gate that nothing compares, and two owners diverge the moment either moves — measured rather than assumed: the hook's pinned 0.9.9 and the lock's 0.16.8 were seven minor versions apart and disagreed about the same tree, 0.9.9 printing `All checks passed!` on a probe carrying RUF061, RUF059 and RUF060 that 0.16.8 reported, with 31 codes inside the selected families existing only in the newer one. `ruff>=0.9` in `pyproject.toml` is the only place the range is written; the resolved version lives in `uv.lock` and nowhere else.
- `$state<T | null>(null)` that is never assigned is a non-reactive constant to the Svelte compiler, so `{#if x !== null}` folds away and the branch — scoped CSS included — is dropped from `dist/` with no warning from any gate. Assign it, and assert that each screen renders what it imports: a card missing from a bundle that builds clean is the failure mode, not a hypothetical.
- `SidecarClient::spawn` hands the child's stderr to its caller and nobody else can drain it. Dropping that receiver does not close the pipe: the sidecar blocks writing its own diagnostics once the OS buffer fills, and every request it owed then times out with no cause. The host takes it and holds it for the process's life; a spawn that fails takes the child's diagnostics with it, so the failure message names the command it tried.
- The host respawns on `IpcError::SidecarLost` — the error the client reports once it has seen EOF — and never on `is_alive`, which is still `true` in the window between the child dying and that EOF arriving. Identity (`Arc::ptr_eq`), not a flag, decides whether a respawn is needed, which is also what keeps a burst of failed calls from spawning one sidecar each.
- `sidecar_path::resolve` looks for `tidal2ytm-sidecar.exe` **without** a target triple: `tauri_build` strips the triple from the name it copies next to the binary, so a `binaries/tidal2ytm-sidecar-<triple>.exe` candidate can never exist. A directory handed to a child as its working directory must exist first — `app_data_dir()` does not on a first run, and a missing one fails the spawn with `os error 267`, which names neither the path nor the reason.
- Building the host needs `dist/` and a `src-tauri/binaries/tidal2ytm-sidecar-<triple><.exe>` placeholder on disk: `tauri_build` refuses a config whose `frontendDist` is missing and an `externalBin` whose file is absent, and `icons/icon.ico` is required on Windows. Run `pnpm build` first, and create the placeholder as an empty file that is never committed (`.gitignore` already excludes `src-tauri/binaries/`). The triple comes from `rustc -vV`'s `host:` field, because the build script reads cargo's `TARGET` and no `--target` is passed; a job that adds `--target` must derive that triple instead. **Any job or hook that compiles the host must create the placeholder first**, or it fails inside the build script before compiling a line of host code — which is how the host crate's tests (`state.rs` and `sidecar_path.rs`) came to have no executor at all.
- Every directory rule in `.gitignore` is root-anchored (`/name/`), because an unanchored `name/` also matches that directory under `src/`, where a frontend or Rust source directory of that name becomes untrackable — `git add src` commits zero files, reports success, and every gate reads green with the feature missing. A rule stays unanchored when the *name* is generated output, since no directory a person would write source into carries such a name and a nested instance of it is still junk. `__pycache__/`, `node_modules/`, `*.egg-info/` and `.ipynb_checkpoints` are the deliberate cases and must stay unanchored on purpose — the last two because anchoring them would be wrong rather than merely redundant, as egg metadata is written beside whichever manifest declared it and a notebook is not necessarily at the repository root. The template's own tool caches (`.webassets-cache`, `.scrapy`, `.ropeproject`) are unanchored for that same reason and need no decision of their own, so the set is not closed and a count of it goes stale the next time a template line is added. Before adding an ignore rule, or anchoring one that is already unanchored, check `git check-ignore -v --no-index -- src/lib/<name>/probe.ts` against the plausible name: a match is a defect only when the name is one a source directory could have.
- `.github/` and `.pre-commit-config.yaml` are Prettier-ignored, so CI and hook YAML is owned by no formatter. Hand-format it; a `pnpm format` pass will not catch a mistake there.
- `[tool.coverage.run] source` lists both workspace members. Adding a member without adding it there puts its production modules outside the `fail_under = 80` gate while its tests still run, so a total regression in them is invisible.
- The sidecar is a onefile PyInstaller build, which excludes modules a larger import graph would pull in, so a missing module surfaces at sidecar runtime rather than at build time. An op needing a new third-party module adds it to `hiddenimports` in `sidecar/tidal2ytm-sidecar.spec` **and** re-runs the smoke test against the staged artifact, not just the suite.
